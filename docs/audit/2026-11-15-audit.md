# Audit Buff Digger — 2026-11-15

Branche auditée : `fix/merci-apres-combat` (373c467, plus `dev/BuffDiggerJournal/Journal.lua` modifié, non commité).
Méthode : lecture de tout le code et des docs, du journal en jeu du 2026-11-15 (15:16–15:33), des issues
GitHub, de la doc d'API générée par Blizzard pour **Forever 1.60.1** (miroir `Gethe/wow-ui-source`, branche
`forever`, build 70938 du 2026-11-13), de Warcraft Wiki. J'ai aussi reproduit le bug hors jeu (§ 3.1).
Rien n'a été modifié dans le dépôt, à part ce fichier.

## Résumé

1. **Le bug « Thank après chaque combat » n'est pas corrigé par le fix 3.** Je le reproduis hors jeu, avec le
   code actuel : il suffit qu'une lecture des auras rende une liste **vide** (et pas une erreur) alors que
   `InCombatLockdown()` est déjà faux. Par exemple : la relecture faite dans `PLAYER_REGEN_ENABLED`, ou un
   donjon hors combat (restriction « Map »). `byInstance` est alors vidé et `ready` reste vrai, si bien
   que tous mes buffs reviennent comme des cadeaux.
2. **La cause est la conception, pas un cas oublié.** On fabrique des « cadeaux » en comparant deux relectures
   complètes. Toute perte d'état devient donc une pose fantôme. Or Midnight (12.1, actif dans Forever)
   rend les auras **illisibles par index ou par ID** pendant toute la durée d'une restriction : selon le
   build, la lecture lève une erreur ou rend nil.
3. Le journal le prouve : à aucune fin de combat `UNIT_AURA` n'a annoncé de nouvelle aura (aucune ligne
   `aura-in`). Les 12 réapparitions viennent toutes de la comparaison.
4. **Recommandation n° 1** : un suivi **événementiel** (`UNIT_AURA` `updateInfo`), qui passe par une
   relecture silencieuse dès que l'état est incertain. Règle d'or : **une relecture ne crée jamais de
   cadeau**, elle ne peut que satisfaire une demande ouverte. L'état « auras secrètes » se lit avec
   `C_Secrets.ShouldAurasBeSecret()` et `ADDON_RESTRICTION_STATE_CHANGED`, plus avec `InCombatLockdown()`.
5. **Avant tout** : un correctif court (issue 1, taille S) qui applique la règle d'or au code actuel, et un test de
   régression rejoué depuis le journal (issue 2, S).
6. **Moins de recettes** : un journal v2 qui **enregistre les charges brutes** des événements, un lecteur
   qui les **rejoue** dans `tests/`, et `/bdj probe`, un auto-test en jeu de 10 s sous restriction
   forcée (CVar `addonCombatRestrictionsForced`, existence dans Forever à vérifier).

## 1. Recherche

  disarmament changes introduced in Midnight, including secrets, will also be active in Forever », et
  « The AuraContainer/AuraButton changes introduced in 12.1.0 will be available as well ».

- Les pages d'API du wiki listent une version « forever (1.60.1) » à côté de « standard (12.1.5) ».
  [GetAuraDataByAuraInstanceID](https://warcraft.wiki.gg/wiki/API:C_UnitAuras.GetAuraDataByAuraInstanceID)
- La doc générée de la branche `forever` (vérifiée ici, fichier `UnitAuraDocumentation.lua`) :
  - `GetAuraDataByIndex`, `GetAuraDataBySlot`, `GetAuraDataByAuraInstanceID` : `RequiresUnitAuraAccess`,
    `SecretWhenUnitAuraRestricted` ;
  - `GetAuraDataBySpellName`, `GetPlayerAuraBySpellID` : `RequiresNonSecretAura`, sans exiger l'accès aux auras ;
  - `GetAuraCasterGUID(unit, auraInstanceID)` existe (le lanceur par GUID et non par jeton d'unité) ;
  - `UNIT_AURA` : `SecretWhenAurasRestricted = true`, charge `unitTarget, updateInfo` ;
  - `GetGroupBuffVisualAlerts` / `HIDDEN_GROUP_BUFFS_CHANGED` (« including linked rank spells ») : Blizzard
    gère lui-même des alertes de buffs de groupe manquants. Piste produit à creuser, non vérifiée en jeu.
  [Gethe/wow-ui-source, branche forever](https://github.com/Gethe/wow-ui-source/tree/forever/Interface/AddOns/Blizzard_APIDocumentationGenerated)
- Autres restrictions de Forever : SendChatMessage `"EMOTE"` exige un événement matériel hors instance
  (comme SAY et YELL) ; les comptes d'essai ne peuvent pas envoyer de messages d'addon ; les barres de nom ne
  s'affichent plus pour les unités très au-dessus ou au-dessous du joueur (`nameplateMaxVerticalDistance`).
  [Patch 1.60.1 notes](https://warcraft.wiki.gg/wiki/Patch_1.60.1/API_changes/notes)

### 1.2 Auras sous restriction (Midnight 12.1, donc Forever)

- « when auras are secret (during combat, encounters, M+, and PvP matches), all of the UnitAura APIs
  will now either return full secrets or nil when called by addons » (build 68209). Puis, au PTR 3 :
  les API par « index, slot, or instance ID will Lua error when called by addons while auras are secret »,
  alors que les API par « spell ID or spell name can still be called by addons as before ».
  « The UNIT_AURA event now delivers a fully secret payload while auras are secret. » « Auras we
  explicitly flag as non-secret will still be returned as non-secret. »
  [Patch 12.1.0/API changes/notes](https://warcraft.wiki.gg/wiki/Patch_12.1.0/API_changes/notes)
  → **Conséquence pour nous** : en combat, la boucle `GetAuraDataByIndex` lève une erreur **ou** rend nil
  selon le build et la fonction. Les deux ont été vus : l'erreur dans le journal du matin, le nil est
  l'explication la plus probable de l'échec du fix 2 (§ 3.1). Il faut traiter les deux comme « inconnu ».
- 12.0.1 (hotfix du 2026-02-24) : Blizzard déclassifie « very long duration buffs » (buffs de raid longs)
  [12.0.1 notes](https://warcraft.wiki.gg/wiki/Patch_12.0.1/API_changes/notes). Les buffs de Forever durent
  1 h. Ils sont peut-être non secrets, donc lisibles en combat par `GetPlayerAuraBySpellID`.
  **Non vérifié** : `C_Secrets.ShouldSpellAuraBeSecret(1243)` en jeu le dira.
- 12.0.5 (PTR 4) : « Aura instance ID values now re-randomize when the player enters an encounter/M+/PvP match. »
  [12.0.5 notes](https://warcraft.wiki.gg/wiki/Patch_12.0.5/API_changes/notes). Donc les IDs **ne sont pas
  stables** dans un boss de donjon ou de raid. Pour un combat ordinaire en monde ouvert, rien ne dit qu'ils
  changent, et le journal suggère qu'ils restent stables (§ 3.1, **à confirmer** par le journal v2).
- 12.0.0 (hotfix du 2026-02-19) : « Fixed an issue where numerous APIs that accept aura instance IDs would stop
  working after a full aura update ». Il faut s'attendre à des cas limites sur `isFullUpdate`.
  [12.0.1 notes](https://warcraft.wiki.gg/wiki/Patch_12.0.1/API_changes/notes)
- Champs `NeverSecret` d'AuraData : `auraInstanceID`, `isHelpful`, `isHarmful`, `isRaid`, `isNameplateOnly`,
  `isFromPlayerOrPlayerPet` (12.0.5 PTR 1). La note 12.1 « AuraData structs are now always fully secret »
  la contredit, et le wiki ne tranche pas. **Ne rien supposer.**
  [Event:UNIT_AURA](https://warcraft.wiki.gg/wiki/Event:UNIT_AURA)

### 1.3 Savoir si les auras sont secrètes (au lieu de deviner)

- `C_Secrets.ShouldAurasBeSecret()` : vrai si les requêtes d'auras rendront « generally » des secrets.
  `ShouldUnitAuraInstanceBeSecret(unit, id)`, `ShouldSpellAuraBeSecret(spellID)` et
  `GetSpellAuraSecrecy` existent aussi. Toutes sont présentes dans la doc `forever` (vérifié).
  [ShouldAurasBeSecret](https://warcraft.wiki.gg/wiki/API:C_Secrets.ShouldAurasBeSecret)
- `C_RestrictedActions.GetAddOnRestrictionState(type)` / `IsAddOnRestrictionActive(type)`, avec
  `Enum.AddOnRestrictionType` = Combat 0, Encounter 1, ChallengeMode 2, PvPMatch 3, **Map 4** (carte
  restreinte : donjon, raid) et Chat 5. L'événement `ADDON_RESTRICTION_STATE_CHANGED(type, state)` est
  « sequenced such that it will always be fired before a restriction becomes active, or after it is
  deactivated ». Pendant son envoi, `IsAddOnRestrictionActive` rend false pour ce type ; il faut lire `state`
  (Inactive, Activating, Active). Présents dans la doc `forever` (vérifié).
  [IsAddOnRestrictionActive](https://warcraft.wiki.gg/wiki/API_C_RestrictedActions.IsAddOnRestrictionActive)
  → **`PLAYER_REGEN_ENABLED` n'est pas le bon signal** pour « les auras sont lisibles ». L'ordre entre les deux
  événements n'est documenté nulle part (**non vérifié**), et la restriction Map existe hors combat.
- Secret values (rappel) : seul le code « tainted » est restreint, c'est-à-dire tout addon. Comparer,
  tester un booléen, indexer, mesurer avec `#` ou utiliser un secret comme clé de table **lève une erreur**.
  La concaténation est permise. `issecretvalue`, `canaccessvalue`, `issecrettable` et `canaccesstable`
  servent à tester. Les CVar `addonCombatRestrictionsForced` et `addonEncounterRestrictionsForced`
  **simulent** les restrictions, mais ne survivent pas au redémarrage.
  [Secret Values](https://warcraft.wiki.gg/wiki/Secret_Values) · [Addon Restriction Tester](https://www.curseforge.com/wow/addons/addon-restriction-tester)
  (avant 12.0.5 elles s'appelaient `secret*RestrictionsForced`). **Non vérifié** : leur présence dans Forever
  (`/dump C_CVar.GetCVarInfo("addonCombatRestrictionsForced")`).

### 1.4 `UNIT_AURA` `updateInfo`

- Charge `unitTarget, updateInfo` : `isFullUpdate` (vrai = tout relire ; les autres champs sont alors
  « likely nil »), `addedAuras` (AuraData[]), `updatedAuraInstanceIDs`, `removedAuraInstanceIDs`. « The
  payload can contain any combination of » ces trois champs. `GetAuraDataByAuraInstanceID` « will not work
  on removed aura InstanceIDs », donc il faut garder en cache ce qu'on savait.
  [Event:UNIT_AURA](https://warcraft.wiki.gg/wiki/Event:UNIT_AURA) ·
  [UnitAuraUpdateInfo](https://warcraft.wiki.gg/wiki/Structure_UnitAuraUpdateInfo) ·
  [Blizzard, « New UNIT_AURA Processing Optimizations »](https://us.forums.blizzard.com/en/wow/t/new-unitaura-processing-optimizations/1205007)
- Le wiki ne dit pas ce qui déclenche un `isFullUpdate` (changement de zone, /reload ?). **Non documenté.**
- Tendance chez les grands addons : oUF ne fait plus de diff en Lua, il délègue l'affichage aux
  `AuraContainer` intrinsèques (12.1). Blizzard le dit lui-même : les conteneurs permettent de « focus more
  on presentation and less on repeatedly querying, diffing, and refreshing aura state ».
  [oUF elements/auras.lua](https://github.com/oUF-wow/oUF/blob/main/elements/auras.lua). Cela ne sert pas à
  *détecter* une pose : c'est de l'affichage, pas un événement Lua. Hors sujet pour nous.
- WeakAuras a arrêté son support, parce que les secrets s'appliquent aussi à l'état de combat du joueur.
  [Icy Veins](https://www.icy-veins.com/wow/news/weakauras-responds-to-addon-limitation-loosening-in-midnight/)

### 1.5 Bonnes pratiques d'architecture (synthèse, sources ci-dessous)

- **Événements** : un seul cadre par module, des `RegisterUnitEvent` ciblés (déjà le cas), lire la charge
  plutôt que tout relire, regrouper les rafales (style AceBucket : déjà fait, `REFRESH_DELAY`).
- **Rafraîchir** : ne recalculer que si une donnée **utile** a bougé (buff de Data.lua, barre de nom
  ajoutée ou retirée). Des tickers d'une seconde, nombreux, coûtent plus qu'un rafraîchissement déclenché
  par un événement. Mesurer avec `debugprofilestop()` et `/etrace`.
  [Events (etrace)](https://warcraft.wiki.gg/wiki/Events) · [MACRO eventtrace](https://warcraft.wiki.gg/wiki/MACRO_eventtrace)
- **Boutons sécurisés** : ne jamais modifier leurs attributs en combat. Re-viser seulement hors combat et
  hors survol (déjà fait). `AnyUp` + `useOnKeyDown=false` (déjà fait et constaté en jeu).
- **SavedVariables** : séparer le compte (réglages) du personnage (`## SavedVariablesPerCharacter` pour
  l'état de jeu, comme `asked`). Migrer avec un numéro de version de schéma plutôt qu'avec des drapeaux
  ponctuels (`thankByHandOn`).
- **Localisation** : `L` en passthrough (déjà fait), plus l'outil de localisation CurseForge
  (`@localization@` du packager) le jour où il faudra traduire.
- **Publication** : BigWigs packager sur tag, `X-Curse-Project-ID` / `X-Wago-ID` dans le `.toc`, jetons en
  secrets. [Using the BigWigs Packager with GitHub Actions](https://warcraft.wiki.gg/wiki/Using_the_BigWigs_Packager_with_GitHub_Actions) ·
  [BigWigsMods/packager](https://github.com/BigWigsMods/packager) · [docs.wago.io](https://docs.wago.io/)

## 2. Revue macro → micro

### 2.1 Produit et périmètre

- **[important] Le périmètre a dépassé la capacité de recette.** On compte 4 900 lignes, 5 fenêtres (Get
  buffs, Give buffs, Requests, Thanks, Phrases), des marqueurs, deux menus, la communication entre addons,
  et deux modes de merci (auto et à la main). La recette compte **68 tests** (`docs/recette-en-jeu.md`), et
  Yann a très peu de temps de jeu. Chaque fonction ajoute des lignes de recette qui ne seront jamais
  jouées. Correctif : un gel des fonctions tant que le rejeu (§ 4) n'existe pas, et un tri (issue 14).
- **[important] La détection des « cadeaux » (buff non demandé, ligne dorée) est la source du bug.** Toutes les
  lignes réapparues dans le journal sont des cadeaux : les demandes avaient été remerciées, et
  `request` était nil. C'est aussi la partie la plus incertaine, parce qu'elle infère une intention à partir
  d'un diff. Sans cadeaux, le bug aurait été invisible, mais l'état aurait été tout aussi faux.
- **[suggestion]** `GetGroupBuffVisualAlerts` (Forever) : Blizzard semble alerter lui-même sur les buffs de
  groupe manquants. À regarder avant d'investir dans « Give buffs ». **Non vérifié.**

### 2.2 Architecture et flux de données

```
UNIT_AURA ──► readMyBuffs (relecture complète, diff byInstance, rang, journal, landing) ──► onBuffLanded
                     │                                                                         │
                     └─► mine (key → rank, giver, expires) ◄── bestBuff / offers / hisBlessing  ▼
NAME_PLATE_* ─► shownPlates ─► listUnits ─► updateIcon / nearbyEntries / giveEntries     toThank / thank()
tickers 1 s (refreshWindow, refreshIncoming), 5 s (refreshThanks), 30 s (refreshAll) ─► UI.fill
```

- **[important] `readMyBuffs` (BuffDigger.lua:353-440) fait cinq choses** : lire, comparer, classer, journaliser
  et décider d'une pose, en 90 lignes et sans frontière testable. Les heuristiques `same`, `renewed`, `had`,
  `prevGiver` et `oldGiver` se superposent fix après fix. Correctif : séparer un **suivi** (état des
  auras, événements « pose » et « relance ») d'une **décision** (merci, cadeau), en fonctions pures
  (§ 3).
- **[suggestion]** Les modules se parlent par `ns` avec des appels tardifs (`if ns.refreshThanks then`).
  C'est correct à cette taille. Les dépendances circulaires Core ↔ UI ↔ Comm restent lisibles.
- **[important] L'état « ce que je sais de mes buffs » n'a pas de notion d'incertitude.** Une lecture partielle
  écrase l'état (`byInstance = seen`, :432), et `ready` ne redevient jamais faux après une perte. Correctif :
  un drapeau `stale` posé dès qu'une lecture n'est pas fiable, levé seulement par une relecture complète
  **non restreinte**, et qui interdit toute pose tant qu'il est posé.

### 2.3 Modèle d'événements, combat, valeurs secrètes

- **[critique] C1. Une lecture vide sous restriction efface tout** (BuffDigger.lua:370-375 et 432-433).
  `if not aura then break end` prend un nil pour la fin de liste. `hidden` reste faux, `byInstance = {}` et
  `ready = true`. À la lecture suivante, chaque buff est « nouveau ». `prevGiver` vaut nil, donc
  `addToThank` crée un cadeau (:346-349), freiné seulement par `THANK_GAP` (60 s). **Reproduit hors jeu** sur
  le code actuel (§ 3.1). Le fix 3 (`InCombatLockdown()`, :357) ne couvre ni la relecture de
  `PLAYER_REGEN_ENABLED` (:1131) si la restriction n'est pas encore levée, ni une carte restreinte hors
  combat (donjon, restriction Map). Correctif : § 3 (issue 1).
- **[critique] C2. Des cadeaux inférés d'un diff** (:405-410 et 346-349). Tant qu'une pose peut naître d'une
  relecture, toute perte d'état (secret, nil, erreur, ID ré-aléatoire en rencontre, /reload) produit des
  merci fantômes. Correctif : un cadeau ne naît que d'un `addedAuras` **lu en direct**, hors restriction
  (issues 1 et 6).
- **[important] `UNIT_AURA` ignore sa charge** (:1140, `a2` non lu). Chaque événement relit 40 index et
  lance `refreshAll`, même pour une aura sans intérêt (nourriture, PV). C'est l'issue #19 § 1, et en partie #7.
- **[important] Le mauvais signal « auras lisibles »** : `PLAYER_REGEN_ENABLED` (:1129-1131). Il faut
  `ADDON_RESTRICTION_STATE_CHANGED` (état Inactive pour Combat et Map) et `C_Secrets.ShouldAurasBeSecret()`
  comme garde, avec repli sur `InCombatLockdown()` si l'API manque (§ 1.3).
- **[suggestion]** Le lanceur passe par le jeton `aura.sourceUnit` (:312-321). Un jeton de barre de nom peut
  être périmé, d'où la garde « la classe ne peut pas donner ce buff » (:323). `C_UnitAuras.GetAuraCasterGUID`
  donnerait une identité stable (le GUID d'un joueur), à résoudre en nom par `GetPlayerInfoByGUID`.
  **À vérifier en jeu** : est-ce lisible hors combat dans Forever ?
- **[suggestion]** Si `ShouldSpellAuraBeSecret` est faux pour nos buffs de 1 h, `GetPlayerAuraBySpellID` les
  lit même en combat (§ 1.2). On pourrait alors suivre une demande en combat. **Non vérifié.**

### 2.4 Gestion d'état

- **[important] Clés d'identité mélangées** : `asked`, `toThank` et `lastThank` sont indexés par
  « Prénom Nom » (`ns.unitName`) ; `justCast` et `onSpellSent` par le prénom seul (UI.lua, `ns.castOn` et
  `ns.onSpellSent`). C'est l'issue #19 § 3. Correctif : une seule fonction `ns.playerKey(unit|chatName)`.
- **[suggestion] `ns.thanksWaiting()` modifie l'état** (:254-260 : `wipe` si l'option est coupée, purge
  des expirés). Elle est appelée depuis le rendu (`askState` pour chaque ligne, UI.lua:940 et 955). Un
  accesseur qui modifie complique le rejeu. Correctif : purger dans un ticker ou un événement, lire sans
  effet.
- **[suggestion] `BuffDiggerDB` est au niveau du compte.** `asked` (anti-relance) est partagé entre les
  personnages. Correctif : `## SavedVariablesPerCharacter: BuffDiggerCharDB` pour `asked`, `buffs`
  (journal #2 ; le compte convient aussi) et `noSource`.
- **[suggestion]** Les migrations se font par drapeaux (`thankByHandOn`, `frenchMessages`, `icons`). Un
  `BuffDiggerDB.schema = n` les rendrait explicites.
- **[suggestion]** `buffKeyOf` construit la table des noms une seule fois (:101-115). Un nom nil au premier
  appel fait perdre ce buff jusqu'au `/reload` (#19 § 2).

### 2.5 Interface

- **[suggestion]** Six tickers permanents : `refreshWindow` 1 s (UI.lua:1426), `refreshIncoming` 1 s
  (Comm.lua:175, qui appelle `ns.listUnits()` même sans demande ni fenêtre), `refreshThanks` 5 s, `refreshAll`
  30 s, plus le ticker des réglages (UI.lua:287). Correctif rapide : sortir tôt si rien n'est affiché et
  qu'aucune demande n'attend (#7).
- **[suggestion]** La fenêtre Thanks et les lignes dorées de Get buffs sont deux interfaces pour un même état,
  avec des règles de bascule (`onGetBuffs`, gift/request). C'est autant de recette en plus. À trancher
  (issue 14).
- **[ok]** Boutons sécurisés : attributs posés hors combat seulement, jamais sous le curseur, nom figé dans
  l'entrée (`who`), et une garde `gone()` contre un jeton passé à un autre joueur. C'est solide.

### 2.6 Communication entre addons

- **[ok]** Message validé (`^REQ:(%a+):(%a+)$`, clé contrôlée dans `BUFFS`, type dans une liste fermée),
  10 s par expéditeur, rien en instance (`IsInInstance`).
- **[suggestion]** `canTalk()` devrait aussi lire `C_RestrictedActions.IsAddOnRestrictionActive(Enum.AddOnRestrictionType.Chat)`
  (12.0.5), plus juste que `IsInInstance()`.
- **[suggestion]** `incoming` n'a pas de plafond global (Comm.lua:152) : beaucoup d'expéditeurs différents font
  autant de lignes et de sons. Plafonner à 20.

### 2.7 Données (Data.lua)

- **[ok]** Tables claires, sources citées, talents pris en compte. Les valeurs vanilla et les IDs de groupe
  restent à vérifier (#2) : c'est le rôle de `/bd log`.

### 2.8 Tests

  semblent stables à travers un combat ordinaire** (indice fort, non prouvé : le journal ne note pas les IDs).

Pourquoi le fix 2 a échoué : il traitait l'**erreur** (`hidden = true`, puis on garde l'état). Une lecture qui
rend **nil** (« full secrets or nil », notes 12.1) quitte la boucle comme une fin de liste : `hidden` reste
faux, l'état est effacé et `ready` reste vrai. Les nombreux `UNIT_AURA` du combat le déclenchaient à chaque
fois.

Pourquoi le fix 3 peut encore échouer. Je l'ai reproduit hors jeu, avec la fausse API de `smoke.lua` et le code
actuel :
```lua

fire("PLAYER_REGEN_ENABLED")        -- readMyBuffs : byInstance = {}, ready = true
```

Ce cas se produit si la restriction est levée **après** le gestionnaire de `PLAYER_REGEN_ENABLED`, ce qui est
possible et non documenté, ou dans un donjon hors combat (restriction Map). Le fix 3 a donc une chance de
marcher en monde ouvert, mais elle dépend d'un ordre d'événements que personne ne garantit.
